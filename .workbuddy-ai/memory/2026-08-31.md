## Audit keamanan ISO Digital System (astro-app)

Melakukan audit keamanan menyeluruh atas proyek (Astro 4 + Solid.js + Cloudflare D1,
Sistem Digitalisasi Dokumen ISO 21001:2018 Yayasan Sinar Putih Edelweiss).
Hasil: `D:\astro-app\LAPORAN-KEAMANAN.html` (3 kritis, 6 tinggi, 7 sedang, 4 rendah).

### Temuan utama (perlu ditindaklanjuti)
- **C-01** `MS_CLIENT_SECRET` ada di `.env` plaintext, **tidak ada `.gitignore`**, dan
  Vite meng-inlinenya sebagai literal ke `dist/_worker.js/pages/api/auth/callback.astro.mjs`
  → secret sudah ter-deploy. **Belum di-rotate** (butuh akses Azure Portal user).
- **C-02** Cookie `iso_user_session` = JSON polos, `httpOnly:false`, `secure:false`,
  tanpa tanda tangan → peran bisa dipalsukan dari browser.
- **C-03** 18 endpoint di `src/pages/api/` tidak punya autentikasi/otorisasi sama sekali.
- **H-01** Status approval + tanda tangan approver dikirim dari klien dan disimpan apa adanya
  (`prs/[id].ts`, `leaves/[id].ts`, `handovers/[id].ts`) → persetujuan bisa dipalsukan.
- **H-02** Stored XSS: `signatureData` tidak divalidasi, disuntikkan ke `<img src="${sig}">`
  di `src/lib/pdfTemplates.ts`, dirender di `<iframe srcdoc>` **tanpa `sandbox`** (warisi origin).
- **H-04** `state` OAuth dibuat dengan `Math.random()` tapi tidak pernah divalidasi di callback.
- **M-01** PUT approval pakai delete+insert → tidak ada audit trail (masalah kepatuhan ISO 21001).
- **M-07** Callback MS hardcode `role:'staff'`, tidak pernah cocokkan `msId` ke tabel `users`
  → ini sebabnya role-based access belum bisa diterapkan.

### Catatan teknis proyek
- Tidak ada SQL injection (Drizzle terparameterisasi), tidak ada `innerHTML`/`eval` di Solid.
- `npm audit --omit=dev`: 13 kerentanan (7 high) — SSRF `@astrojs/cloudflare` `/_image`
  (GHSA-qpr4-c339-7vq8), `undici`, `ws`. Fix penuh = upgrade ke adapter v14 + Astro 5 (breaking).
- Belum ada `src/middleware.ts` — ini titik paling efisien untuk memasang auth.
- Meeting ID: `MTG-${Math.random()*10000}` → hanya 10.000 kemungkinan.

### Konvensi / preferensi
- Pengguna berbahasa Indonesia; minta saran keamanan dalam konteks dokumen & data.

## Lanjutan: verifikasi E2E lokal + perbaikan bug (deploy 33e592ef)

Sesi ini membaca ulang `LAPORAN-KEAMANAN.html`, memverifikasi tiap temuan, dan
menemukan **dua bug live** lewat pengujian end-to-end lokal (wrangler pages dev
+ D1 lokal, terisolasi dari produksi):

### Bug yang ditemukan & diperbaiki
1. **Regresi M-05**: `prCreateSchema` menandai `pr_number` sebagai **wajib**,
   padahal server menghasilkan PR number sendiri & mengabaikan nilai klien.
   Akibatnya `POST /api/prs` gagal 400 (UI tidak mengirim `pr_number`).
   → `pr_number` dijadikan `optional()` di `src/lib/schemas.ts`.
2. **H-01 belum benar-benar ditegakkan**: `hasRole()` pakai hierarki
   `ROLE_RANK = {admin:3, approver:2, coordinator:1}` → `approver ≥ coordinator`
   bernilai TRUE. Seorang `approver` bisa membersihkan step `koordinator`, dan
   `admin` bisa melompati rantai. E2E membuktikan `pr_approvals` step1 & step2
   ditandatangani user `id=3` (approver) — satu orang menyetujui semua step.
   → Keputusan approval di `decideApproval` (`src/lib/approvals.ts`) diganti
   **exact match** (`user.role === requiredRoleFor(step)`). Hierarki `hasRole`
   tetap dipakai untuk gate otorisasi umum (mis. edit meeting/asset).

### L-03 diperkeras
- `callback.ts`: `resolveUser` kini mengembalikan `registered:false` bila akun
  tidak ada di tabel `users` → login ditolak (`user_not_registered`). Sebelumnya
  auto-provision sebagai `staff`. Domain `@edelweiss.sch.id` tetap diwajibkan.
  Aman karena user produksi (id 1-4) sudah ada di tabel.

### E2E lokal (semua hijau)
Unauth GET → 401; create PR → 201; requester self-approve → 403; approver di
step koordinator → 403; koordinator→approver→admin tiap lanjut 1 step; final
→ Approved; re-approve → 409. `pr_approvals`: step1 approver_id=2 (coordinator),
step2=3 (approver), step3=1 (admin). `audit_log`: created + 3 approval (actor
id/role). Admin tidak bisa lewati step koordinator (403).

### Deploy
`npx wrangler pages deploy dist` → **`33e592ef`** (production/main).
Verifikasi live: `/` 200, `/api/prs` & `/api/leaves` 401, `/api/auth/me` 200,
CSP (nonce + strict-dynamic), HSTS, X-Frame-Options aktif.

### Status akhir temuan
- Kritis C-01..C-03: SELESAI (C-01 rotasi Azure masih ditunda user).
- Tinggi H-01..H-06: SELESAI (H-01 baru benar-benar valid setelah exact-match fix).
- Sedang M-01..M-07: SELESAI.
- Rendah L-01 (.gitignore), L-02 (127.0.0.1), L-03 (reject unregistered),
  L-04 (PII sample dihapus): SELESAI.

## Auto-Provisioning Domain Edelweiss, Hak Akses Dokumen Pribadi & Notifikasi Email Berjenjang (deploy bd77057c)

### 1. Auto-Provisioning Login Microsoft 365 (`src/pages/api/auth/callback.ts`)
- **Masalah**: Login ditolak (`user_not_registered`) untuk akun baru seperti `mikhail.pasaribu@edelweiss.sch.id` karena pengetatan L-03 sebelumnya mematikan auto-provisioning.
- **Solusi**: Akun dengan domain `@edelweiss.sch.id` kini otomatis dibuatkan data akun baru di database dengan role default `staff`. Tidak perlu lagi pendaftaran manual. Begitu staf login pertama kali via Microsoft 365, akun langsung aktif.

### 2. Privasi & Scoped Document Visibility (`prs/index.ts`, `leaves/index.ts`, `handovers/index.ts`)
- Staf biasa (`role === 'staff'`) **hanya dapat melihat dokumen yang mereka buat sendiri**:
  - `GET /api/prs`: difilter `requesterId === user.id`.
  - `GET /api/leaves`: difilter `requesterId === user.id`.
  - `GET /api/handovers`: difilter `recipientId === user.id`.
- Koordinator (`coordinator`) melihat dokumen milik sendiri + dokumen unitnya.
- Approver (Keuangan/HRD) dan Admin melihat seluruh dokumen untuk verifikasi & approval.

### 3. Notifikasi Email Berjenjang via Microsoft Graph API (`src/lib/notifications.ts`)
- Memanfaatkan izin aplikasi Azure Entra ID `Mail.Send` via endpoint Graph API `https://graph.microsoft.com/v1.0/users/ict@edelweiss.sch.id/sendMail`.
- **Alur Notifikasi Berjenjang**:
  - **Saat Dokumen Dibuat (Tahap 1)**: Mengirim email notifikasi resmi ke email Koordinator Unit terkait.
  - **Saat Tahap 1 Disetujui (Tahap 2)**: Mengirim email notifikasi ke email Tim Accounting / Keuangan (`approver`).
  - **Saat Tahap 2 Disetujui (Tahap 3)**: Mengirim email notifikasi ke email Ketua Yayasan / Pimpinan (`admin`).
  - **Saat Dokumen Selesai Disetujui (Final)**: Mengirim email selamat & konfirmasi ke Pemohon dokumen bahwa dokumen telah resmi disetujui dan siap diunduh.
  - **Saat Dokumen Ditolak**: Mengirim email pemberitahuan penolakan beserta catatan alasan penolakan ke Pemohon.
